# 遊玩萬熊之熊

## 確立目標

讀取 `bears_history`，掌握目前選單、角色狀況及近期操作。
若歷史紀錄為空，執行 `/start` 前先詢問，因為它可能啟動角色建立流程。
從機器人的實際回覆中尋找說明指令及選單選項，不要自行編造指令。
若驗證失敗，請使用者在自己的終端機完成 `npm run login`；不要自行取得憑證。

對於未限定範圍、且沒有任務專屬額度授權的遊玩請求，最多執行 10 次會改變狀態的操作，然後回報。
任務已有使用者明確授予的專屬額度時，依該任務的有效額度與界線執行，不因一般10次上限重複要求同類授權。本 skill 不依賴帳號專用的本機 `AGENTS.md`；若工作目錄另有適用規則，仍須遵守。找不到本機文件或只見歷史角色紀錄時，不得推定已有額外授權，也不得將其他帳號的授權套用到目前使用者。
遵守使用者後續設定的較低額度，並在有明確完成條件的任務達標時提早停止。
直接執行 `/skill:bears-equipment-strategy` 是該 skill 所定義、最多 9 名角色的批次配裝要求，改用其中的逐角色額度；這個例外不適用於一般遊玩請求。
僅要求策略的請求允許觀察，不允許改變遊戲狀態；直接執行上述 skill 則包含其明列的切換與嚴格提升換裝授權。

## 指令參考

選擇遊戲指令或回答遊戲功能是否可用前，先閱讀 [commands.md](commands.md)。
該文件依用途整理已觀察到的指令，並附上狀態變更與授權警告。完整的 117 個結構化 tools、Telegram prefix 與參數見[完整對照](references/structured-tools.md)；優先使用已封裝的 tool，不自行拼接子命令。遊戲 `/history` 使用 `bears_game_history`，不得覆寫或取代只讀 Telegram 聊天紀錄的 `bears_history`。
這份參考資料來自機器人的實際說明與回覆，但不保證語法、費用或規則仍然適用。
不確定時，重新查看即時說明或選單；不要將範例視為授權。

### 結果消費與補查

`bears_history`、`bears_send`、`bears_click` 與結構化遊戲指令在 Codemode 直接回傳物件；不逐步手寫 JSON／尾端 source ID 解析。只有舊文字結果才呼叫本機 `bears_decode_result({result})`。`bears_world`／`bears_codex`／`bears_life_codex`／`bears_public_character`／`bears_optimize_equipment` 載入新版 schema 後也直接回傳物件，保留原 root 欄位；先查 `outputComplete`／`outputReasons`，省略 payload 不代表空清單或可套用推薦。這個欄位不替代來源時效、`completeness` 或 `applicable`。`bears_original` 分頁及其他專用摘要依各自協定消費，不假設所有 tools 格式相同。

基礎指令的 `submitted`、bot 更新與 `outcome=unknown` 都不代表成功；核對原文才能確認結果。`code`、錯誤、`complete=false` 或缺頁不可忽略。完整且明確的回覆不額外查 history；只有延遲、缺頁、來源或結果不明才補查，仍最多兩次、不重送。同 ID／revision 不因新 request 改綁操作；watch 先到且沒有在先、同角色／分支的 outgoing 證據時，保留歸屬未知，不重送以補歸屬。必要的新角色／費用／按鈕核驗不是重複查詢。

快照 `data.blocks` 各自保留來源及新鮮度，`nonAtomic=true` 不是原子狀態；新 snapshot ID 不會刷新舊資料，也不會使 `riskVerified` 變成 true。先處理影響下一步的缺口，不為填滿無關欄位增加查詢。使用者改做規劃或 coding 時，保存已確認中斷點，不新增遊戲動作。

### 本機持久化帳本

帳本預設由既有 Telegram 連線的本人 ID 自動分庫，不需手動帳號標籤；未確認 ID 時不得推期初或為查帳額外登入。優先消費指令的 `accounting.confirmedMpCost`／`mpAfter`，不另寫 Codemode 扣帳腳本。成本不等於餘額；unknown 不補零，落盤失敗不表示遊戲失敗，也不重送補帳。

`bears_ledger_status` 查歷史資源與缺口，`bears_ledger_trace` 查帳內來源，`bears_ledger_report` 列條件差異及區間效率，`bears_ledger_checkpoint` 只預覽。trace／report 續頁附同一 `snapshot`，依 `nextOffset` 串接 JSON 片段。它們不查 Telegram、不刷新資格，不取代本節的 `bears_original`／新 history 核驗或既有安全護欄；未知防護、未支援格式及角色歸屬仍須明列。

帳本由同一投影提供單一最新檢查點；日誌只留重要變化與來源，避免三處重複流水。固定路徑匯出須由使用者獨立執行 preview／write，備份、重建及停用均不恢復遊戲。啟用、資料位置、格式範圍、`/bears-ledger backup`／`rebuild` 與復原程序見[帳本參考](references/ledger.md)；不為部署 reload 正保留挑戰的工作階段。

### 掛機的狀態變更
啟動 `/idle` 代表授權遊戲端持續活動，而非僅一場手動戰鬥；必須取得明確許可，並遵守 BOSS 限制。
起掛前交叉核對公開地圖的房間來源層、`boss` 標記與原生房間回覆；原生當下只列普通怪，不足以將公開標為 BOSS 的房間當作非 BOSS 起掛點。標記矛盾或缺漏時，改選已確認的非 BOSS 房並沿新出口逐房核驗，不在該房試掛。公開 `boss=false` 仍不證即時安全，裂隙非安全房也不得作為起掛點。
`/stopidle` 會領取獎勵並結束掛機模式，`/idlestatus` 則只檢視進度。
移動、攻擊及施法也可能結束並結算掛機模式。

## 依據證據選擇操作

以 Telegram 回覆作為 HP、資源、背包、冷卻時間及操作結果的準據。
使用 `bears_world` 檢視房間 ID、方向出口、安全房間、NPC 及 BOSS 標記；其公開快照可能落後於遊戲。
使用列出的出口，不要從網格座標推測連通關係。
最短路線不一定安全：優先選擇已知的安全房間，並避開 BOSS 房間，除非戰鬥是使用者目標的一部分。
每次只移動一個房間，確認目的地後再繼續。

戰鬥前，檢查目前 HP、可用的恢復手段及已知逃跑路線。
血量或敵人難度不明時，先檢視，不要開始另一場戰鬥。
危險遭遇後，先比較 HP 與資源變化，再決定恢復、撤退或繼續。

套件提供 `bears_plan_combat` 唯讀單步決策 tool。有足夠數值做承傷預算時，優先以 `bears_combat_snapshot` 的 `snapshotId` 綁定本人原文，再交給它計算；先讀取 tool schema，不要求使用者手動提供 JSON。風險假設及其來源仍須另外核對，舊版完整數值輸入只作條件計算。四組 evidence 需保留最近 60 秒內的訊息 ID、revision 與 Unix 秒時間。未知上界保留缺漏，不把 ATK、consider 或歷史實傷冒稱理論上界；完整機制未確認時不得標示 `mechanicsComplete=true`。`snapshotId` 可綁定原文狀態，但 planner 不證明外部承傷上界或操作授權；`ready` 只表示符合所提供的預算，不是安全證明。依建議出手前仍核對來源、當前身分、已知機制與授權，操作後重新觀測。`recover` 不授權自動自療、逃跑或退出星塔；工具的其他狀態表示未產生可用的預算建議，不是所有戰鬥的禁令。符合下節使用者授權的有限試探可獨立判斷，不為取得 `ready` 捏造數值，也不把目標 HP 為 0 當成掉落或整趟任務完成。

### 以已勝紀錄為邊界，往上試一階

- 本人實際勝場、當時裝備／技能與承傷紀錄是能力邊界的有效證據，不只拿來列候選。先核對目前角色、HP／MP、裝備與技能差異、目標現身、已知特殊機制、勝算及退路；不因欠缺完整公式或理論承傷上界，就一律禁止重打已勝區間。
- 在使用者允許的試探範圍內，可嘗試緊鄰已勝邊界上方的一階。「一階」是綜合等級、HP／攻防、特殊機制與本人實戰紀錄的下一個可比較強度，不是等級＋1，等級不必連續；不只按等級或清單相鄰認定可試。下一候選若強度跳升明顯、機制差異過大或已有危險證據，先補強或回打已勝區間，不硬試、不連跳更高階。
- 逐筆出手後核對實際承傷、HP／MP與新階段。有危險立即撤退、恢復或回已勝區間，不預排連打；使用者限定一次就只測一次，已有持續鄰階試探授權時不重複要求同類授權。一次普攻仍可能包含先機、未命中反擊或多段效果，不能將「只打一手」當作必定只受一次傷害。
- 保留實測的角色、裝備、目標階段、命中／未中、先機與反擊來源。可結合條件差異比較下一候選，但不能將樣本當成其他王、角色或塔層的確定傷害，更不能冒稱理論最大值；比較能力邊界不等於套用傷害公式。明顯致死測試、未知費用付款及其他未授權操作不在此範圍。

### 高難度路線受阻時，先比較較容易的 BOSS

星塔或高階素材王受阻，不等於只能研究高階配裝、精煉或要求使用者補證。已有本人打王授權時，依下列順序選替代行動；不先宣稱有容易王可打，也不預排攻擊。

1. 將缺口限定到原行動：例如塔內封頂與減傷順序，只限制依賴該順序的戰鬥；精煉漏價只限制該筆付款。若某項未知確實共用，說明它如何影響新候選，不直接沿用「所有 BOSS 都缺完整公式」的結論。
2. 先比較已知低風險流程與較容易野外王的本人收益。金幣、王之精魄、可用材料都可作持續強化資源，不要求每場直接提升現穿裝備，也不因滿級、曾勝或已登錄排除。有已確認的本人可用裝備／素材掉落機會，也可依合理預期效益選為有效手段；不要求每場必掉或立即強化。歷史流程可支持能力邊界與有限試探的判斷，仍須核對當前身分、資源、配裝與機制差異；不要求每場先取得完整公式。
3. 依最新 history 核對目前角色與中斷狀態。選裂界 BOSS 前，先查本角色最近正式勝回執及已觀察的個人討伐冷卻；已知同王仍在30分鐘限制內就排除該候選，不用公開存活、滿血現身或 `/consider` 代替本人資格。再以一次 `/boss_respawn` 比較未受限制的存活候選、已觀察出口與安全恢復點，不原地等王、不輪詢。到場核現身、本人 HP／MP、裝備／技能條件及 `/consider`，逐筆確認後才選下一筆。這項資格檢查也必須在為該王臨時換裝或施放支援技之前完成；遭拒後先核原裝恢復與資源，不改攻擊指令測試同王。
4. 只核對這場決策會用到的承傷、先機／未中反擊、特殊效果、技能成本與退路。不要求先取得整個遊戲所有傷害公式，也不把不依賴的塔內封頂或未知新裝被動追加為低階戰鬥前提。已勝或使用者允許的鄰階，依前節能力邊界與當前證據逐筆嘗試；不把 ATK、consider 或樣本填成理論上界。若發現強度明顯跳升、已知危險、身分／資源不符或退路不成立，停止該場並轉其他候選；單純理論上界未知不是全數停打的理由。
5. 符合條件就實際出手；若是有限試探，先核當手結果再決定續戰或撤退，若已正式擊殺則核回執、本人收益及資源，再決定下一筆；不得只交付候選表。預期掉率、正式勝場、實際掉落與裝備提升分開記錄，單場未掉目標物不判為路線無效，也不能為追回未掉落而等王、輪詢或預排刷怪。若沒有通過核驗的候選，列該候選的具體失敗條件，不將未審候選一併否定。無新資料時不重查相同負面來源，也不重複輸出「無新增成果／未證明全域不可行」當作續行。

使用者改要求先修正程式或流程時，先完成該工作，不以舊 Goal 催促恢復遊戲。本節不新增交易、切角、掛機、危險測試或付款授權；planner 的數值與證據協定保持不變，但不得將其缺少建議誤作已授權有限試探的全面禁令。

### 缺材料時的安全取得流程

遇到王之精魄或其他已確認的 BOSS 材料缺口，不能只因合成入口不明、先前某件進化網站分數未變，或 BOSS 已登錄圖鑑就停止。
先用目前角色的 `/forge` 或已確認的配方核對目標、現有數量與缺口，再查 `bears_codex` 的材料掉落與位置，並用遊戲 `/boss` 交叉核對；荒原巨角獸（巨獸的領地，Lv80）是王之精魄70%機率的候選，不保證掉落。
比較可達性、恢復、掛機中斷成本及角色自身收益，選最容易安全擊殺的來源；已登錄 BOSS 可以為實際材料缺口重打，但不得僅為研究重刷或原地等重生。
已有戰鬥授權時，確認目前角色、滿足恢復需求的 HP／MP、可走的非危險出口與 BOSS 現身，再依本人能力邊界逐場出手。參考即時 `/consider` 與已知機制，但不將「輕鬆／有把握」或某個勝率作為唯一硬門檻；也不以歷史勝算、公開地圖等級或掉率省略當前核驗。若綜合證據顯示明顯超出能力或沒有可用退路，改選其他來源。
每場結算後確認精魄是否實際入帳、HP／MP 和王重生狀態，再決定是否還有安全可執行的下一場；若 HP 低於50%且下一擊不能安全結束，撤退。
若本輪無安全可打的王，記錄具體原因（例如當前勝算、未現身、路線或授權）與下次驗證條件，恢復受影響角色的安全掛機；只有逐一排除已知候選後才稱材料路線暫時無法推進。
評估裝備時，先閱讀[裝備評分策略](../bears-equipment-strategy/SKILL.md)，使用 `ATK／DEF／INT／AGI = 1／1／1／1` 作為未指定策略時的預設；使用者要求依職業安排時依該 skill 選擇有證據支持的 profile。
權衡已觀察到且與職業相關的屬性、被動效果及成本；不要假設稀有度越高就一定越好。
不要編造掉落率、屬性公式、最佳配裝或有利可圖的刷怪循環。

1. 執行型 tool 的呼叫前，Agent 必須確認使用者授權涵蓋本人、流程、費用及副作用，再填入 `scope` 的角色、快照與次數／時間／費用上限。
   - `scope` 或 plan ID 不是授權憑證，也不允許使用者原本禁止的操作。
   - 存款另外提供明確 `policy`；不將本 repository 的帳號比例套用到其他使用者。
   - 仍在掛機時先依既有授權另外結算；執行型 tool 不暗中停掛或復掛。
2. 僅以上固定流程內，將「讀原文、逐筆確認、依新結果選下一步」委派給 tool 狀態機。Agent 不需在同一次呼叫的內部每一步再啟動模型決策，但必須核對整體回傳。
   - 每筆子動作經既有 tools 與 hooks，操作前重新比對來源及實際指令；單指令、其他流程及 Auto Idle 不得並行插入。
   - 這不是任意 codemode 迴圈、批次路線或持續刷怪授權。一般戰鬥與工具呼叫仍遵守逐筆 Agent 核對規則。
3. `confirmed` 才表示流程已驗收；`ready` 不代表安全或執行許可。其他狀態保留缺漏、已確認步驟、實支與最後狀態；部分成功後不重跑整批或自動回滾。
4. 結果不明最多補讀 history 兩次，不等待、不重送；取消、死亡、限流、身分或費用不符時停止。reload／session／tree 切換後不恢復操作。新版流程的 `data.interruption` 保留原目標、已確認位置、最後來源及未決操作，只供重新核驗；`data.rpcDiagnostics` 分開子工具與 library RPC 呼叫，不等於網路封包或限流根因。不沿此摘要重送或恢復操作。
5. 戰鬥事件支援標籤式 replay 及測試已涵蓋的原生技能回覆，不泛化到其他格式；新 parser 須 reload 才會載入。首次治療前 HP 未提供時，實補保持 unknown，名義治療不當實補；敵 HP 為 0 未正式結算不算勝利，未知盾耗次不作生存預算。
6. parser 未支援或沒有完整費用證據時停止相依步驟，不以付款、試裝、盲打或測致死招式補證。合成 fixtures 與離線測試不代表實機格式或戰鬥安全已驗證。

## 單次配裝任務

使用者要求「幫我抓背包並換上更強裝備」時，由 Agent 串接既有工具，不要求使用者提供 JSON。
先讀 history，再依序取得 `/status` 與 `/inventory all`，使用裝備評分策略 skill 決定固定權重，呼叫 `bears_optimize_equipment` 查看來源與缺漏。
工具只計算及診斷，不會替 Agent 查詢、換裝或啟動背景工作。
標準裝備列的名稱、等級、資格與屬性格式全部符合已確認協定時，optimizer 可由完整背包判定部位，並將該列未出現的四軸屬性視為零；特殊名稱、技能、被動、套裝或未知格式仍須 inspect 並保守阻擋。
使用者明確要求 `/autoequip` 時，可依即時指令說明執行，不需先完成自訂評分或取得完整背包；執行後重新查詢狀態及背包確認結果。
若誤查 `/inventory` 而看到「較弱裝備未列出」或分頁提示，改查一次 `/inventory all`，不要直接判定無法補足；只有全列回覆仍缺項、截斷或格式未知時才停止套用。不猜隱藏編號，也不販售或銷毀物品來縮小背包。
只有剩餘缺漏可由已確認的 inspect 語法補足時才補查；必須綁定最新背包編號與唯一名稱，無法區分重名物品時停止。

全列背包拆成多則時，先核對完整連續回覆；只讀最後一則 history 不能補回遲到中頁。當 send 缺中頁時，以 history 取得涵蓋該次首頁至尾頁的回覆，不重送 inventory，也不把展示省略等同解析缺項。先完成必要的 skills 查詢，再依序取得 status／完整背包及 inspect；評分前無須因查過 inspect 就再次刷新 inventory。新的 inventory 觀測會清除既有 inspect 綁定，必要刷新後應重新核對綁定狀態，不把舊成功查驗當新推薦。背包及角色的五分鐘新鮮度檢查仍適用；失效或過期時停止套用，不以此流程延長期限。

一般單次配裝任務最多 6 次 equip 嘗試、10 次狀態變更、40 次查詢（含 history／翻頁／inspect）及 5 分鐘，以使用者較低上限為準；從第一次查詢計時並逐次記帳，達限回報部分結果，不自動重開。
任務已有專屬授權時依其額度及資源界線執行；此例外不解除快照完整性、逐件確認、效果取捨或結果不明時停止的要求。
這是 Agent 流程額度，不是 Telegram 工具的交易防火牆。
一般單一角色配裝流程不啟動掛機、不切換角色；若已在掛機，停止並確認結算後重新擷取背包。直接執行 `/skill:bears-equipment-strategy` 時改依該 skill 的批次流程、切換授權與逐角色額度處理。

若工具回傳可套用推薦，授權完整時優先用 `bears_equip_upgrade` 的既有單件流程，避免自行沿用列號；每次最多換一件嚴格提升並重新驗收。optimizer 的 `itemReferences` 綁定本次角色、完整背包版本及已觀察屬性，不是後端永久 ID 或授權；stale／歧義參照不改用名稱或另一列號。原生 `bears_equip` 仍用列號，並未自動接入參照保護。

手動單步換裝前仍須重新查詢 `/inventory all` 並重算，確認角色、目標名稱、編號、數量、精煉、詞條、穿戴資格與目前裝備均未改變。
平手保留現有裝備，不因負分自行卸裝；未授權忽略技能／被動／套裝差異時不替換涉及取捨的裝備。
確認當前 equip 的語法、費用與副作用後才可送出；未知或非預期費用不推定為免費。
換裝後用新背包／inspect 確認目標已穿戴；總分預測、送出命令或 `/status` 總屬性不能單獨證明換裝成功。
回覆不明最多讀 history 兩次，仍不明即停止，絕不重送；速率限制、取消、死亡、角色改變或快照不完整同樣停止。
部分成功後不自動反向換裝，回報已確認、未完成及結果未知項目；恢復原配裝須重新取得授權及觀測。

回報時區分「玩家說法」、「其他資料支持」與「已實測確認」，並交代適用條件；證據不足時保留為待驗證線索。
